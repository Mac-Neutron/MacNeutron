## Conventions and legend

* **Dispatch.** PE side: `UNIX_CALL(slot, &params)` -> `__wine_unix_call(handle, slot, params)` (winemetal_thunks.c:15, wineunixlib.h:312). Unix side: `__wine_unix_call_funcs[slot](void *params)` (winemetal_unix.c:3385). 153 slots (0..152); slot 83 is NULL. A parallel `__wine_unix_call_wow64_funcs[]` (unix.c:3541) exists for 32-bit PEs (same functions except SM50 `thunk32_*`; `WMTMemoryPointer` grows a `high_part` on i386) and is out of scope. Every unix function returns `STATUS_SUCCESS` except `_WMTBootstrapRegister/LookUp` (121/122), which return `STATUS_UNSUCCESSFUL` on Mach failure; the PE asserts `!status` in debug builds for all other slots (winemetal_thunks.c:15).
* **Parameter block.** One C struct per call, `#pragma pack(push, 8)` (winemetal_thunks.h:7), passed by pointer; the host reads input fields and writes `ret*` fields **in place** in that same block (so the params block is itself an in/out buffer of `sizeof(struct)` bytes). SM50 slots (74-88) use `airconv_thunks.h` structs which are NOT packed (plain LP64: all 8-byte aligned pointers/size_t, `int ret` last). Slots 0 and 1 pass a bare `obj_handle_t*` (8 B), not a struct.
* **Pointers are caller-address-space pointers.** `WMTMemoryPointer` / `WMTConstMemoryPointer` (winemetal.h:125,159) are 8 B (`ptr` only; on i386 + `high_part`). Several slots pass the same thing as a raw `uint64_t` (slots 8, 26, 32, 114) - all of these are plain addresses that the host dereferences directly (Wine PE and unix lib share one address space). A forwarder must copy-in/copy-out every region listed in the "reads"/"writes" columns and rewrite pointers.
* **`obj_handle_t`** (winemetal.h:28) = `uint64_t` raw Objective-C object pointer on the host (no handle table, no validation: the host messages whatever the caller sends). Slot-specific exceptions: sm50_* handles (74-88) are raw host C++ pointers (`sm50_ptr64_t`), slot 108's "listener" is a host `malloc` struct, slot 72's view is a macdrv opaque pointer, `NT HANDLE` values in slots 104/146 are Wine event handles typed as `obj_handle_t`, and `handle` in slots 92/94-96/114 carries a plain value (colour-space enum, CGDirectDisplayID, guest pointer).
* **Ownership of returned handles.** `+1` = caller owns (new*/alloc/copy/create), release via slot 1. `ar`/"autoreleased" = valid only while a host autorelease pool on the calling host thread lives (pool = slot 10; the unix library itself never creates pools except inside slot 128); retain via slot 0 to keep. `borrowed` = owned by another object.
* **Column "memory the host reads/writes"** lists ONLY memory referenced through a pointer (beyond the params block itself). "size source" is given inline: `const` = sizeof(struct X); `count x elem`; `NUL` = NUL-terminated string; `list` = linked list via `next`; `unbounded` = no bound in the call.
* **Column "blocks?"**: `YES` = host thread can block on something external (GPU wait, drawable wait, main-queue dispatch_sync, CFRunLoopRun); `slow` = synchronous but finite compile / file IO / sqlite work; `no`.
* **Field annotations** (fields column): `@N` = byte offset in the block; `[out]` = written by the host; `[in]` = read (default, unmarked fields are inputs).

## 1. `wmtcmd_*` command nodes (encodeCommands: slots 36, 37, 38)

Common header (every node): `struct wmtcmd_base` = `{ uint16_t type @0; uint16_t reserved[3] @2; WMTMemoryPointer next @8 }`, 16 B (winemetal.h:918). `type` is the per-encoder enum (blit/compute/render below); the host selects the node struct from `type`, so **the node size is implied by the type, never stored**. The list is a singly linked list through `next.ptr`; the walk ends at `next == NULL` (there is no count, no end marker and no total size). Nodes live anywhere in caller memory (PE builds them in a bump allocator). All numeric fields are plain data; `enum` members are 1-, 2- or 4-byte as noted by the declared underlying type (winemetal.h). Types outside the table hit `default: assert(!next->type)` (unix.c:703, 838, 928): a no-op in NDEBUG builds and a silent skip, but the walk still follows `next`.

Rows are per enum value. "Handles" = `obj_handle_t` fields (must be translated / validated when forwarding). "Pointer fields" = non-`next` WMTMemoryPointer fields and how the host learns their size. Unix handler line numbers are for `winemetal_unix.c`.

Semantics a forwarder must preserve:
* **Order and batching.** Nodes execute in list order on the encoder passed in `encoder` (the host never changes encoders inside a call). Compute `SetPSO` sets a call-local `threadgroup_size` consumed by later Dispatch/DispatchThreads/DispatchIndirect nodes in the SAME call only (unix.c:835, 863); state is reset to {0,0,0} at the start of every call.
* **Inline vs pointer payloads.** The only out-of-line payloads in all 3 node families are the four pointer fields above (`setbytes.bytes` x2, `setviewports.viewports`, `setscissorrects.scissor_rects`); everything else is inline in the node, so a serializer that copies `sizeof(node)` per `type` plus those four regions is complete. `setbytes.length` is uint64 (Metal limits it to 4 KiB); viewport/rect counts are uint8.
* **Handles in nodes are never written back** (nodes are read-only for the host; the host does not modify node memory).
* **`SetViewport`/`SetScissorRect` (single) carry the struct inline** (`viewport` 48 B @16, `scissor_rect` 32 B @16) and are bit-cast to MTLViewport/MTLScissorRect.
* DXMT-specific render nodes (types 29-32, 37-40) bind buffers at fixed indices defined by `enum SM50_BINDING_INDEX` (airconv_public.h:23-37): 3 index buffer, 4 draw/indirect arguments (object-stage buffers), and run mesh-shader draws.
