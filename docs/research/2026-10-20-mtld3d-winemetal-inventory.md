# mtld3d 0.14.1 on winemetal: the inventory (2026-10-20)

D3D9 spec §5.1. Three read-only passes over mtld3d's Unix side (`build/wine-arm64-src/dxmt/mtld3d/unix/unix/src`) against
DXMT's winemetal API and the VM's forwarding (`eac-vm/metal/wm`, `docs/research/2026-10-15-vm-route/winemetal-calls.md`):
resources and state objects, command submission and encoding, presentation and platform code. Line numbers are
mtld3d 0.14.1's.

#### mtld3d Unix side -> winemetal: device, resources, state objects (inventory)

Read-only inventory, worktree `.claude/worktrees/upstream-master`, 2026-10-20. Paths are relative to
`build/wine-arm64-src/dxmt/mtld3d/unix/unix/src` (mtld3d) unless they start with `winemetal.h`/`winemetal_unix.c`
(= `build/wine-arm64-src/dxmt/src/winemetal/...`) or `calls.c` (= `eac-vm/metal/wm/calls.c`, the VM mode table).
VM modes: Q = queued (guest returns before the host runs), S = sync (waits for the host), L = local.
Area files read: `metal.rs`, `metal/{device,buffer,texture,sampler,pipeline,shader,capture,handle,null_texture,transient,clear_quad,blit,upload_quad,depth_transfer}.rs`, library/pipeline parts of `metal/present.rs`, `encoder/compile.rs` + `compile/libraries.rs`, `shader_programs.rs`, `shader_prewarm.rs`, `translation.rs`, `handlers.rs`, and a crate-wide grep.
`shader_programs*`, `shader_prewarm.rs`, `translation*` and `encoder/compile*` contain no Metal selectors: they only pass `MetalHandle<...Kind>` around and call `metal::compile_shader_library` / `metal::create_render_pipeline` inside `autoreleasepool` (compile.rs:562, shader_prewarm.rs:335, encoder.rs:9420).
Not used anywhere in the crate (grep: "not found"): MTLHeap, residency sets, binary archives, function constants, indirect command buffers, shared textures / IOSurface, buffer-backed textures, MTLEvent/Fence in this area, counter sample buffers, `makeAliasable`, hazard-tracking or CPU-cache options, `ShaderWrite` usage, texture `getBytes`.

#### Getter note (Q or S)
Slots 39-44 (texture getters) and 5/6/24/49-52 (device queries) are `QUERY` entries in calls.c (mode S): each takes a guest->host round trip, so uncached use in hot paths (texture dimensions in command.rs encoding, device queries per frame) costs about 0.3 us spinning to 26-48 us parked (README: ring figures).

#### Gaps ranked by size
1. **Vertex descriptor missing from `WMTRenderPipelineInfo`** (pipeline.rs:47-74). New struct block or new function; changes struct size/arg walk in `calls.c` (guest + host). Alternative is rewriting mtld3d's generated MSL to pull vertices (much larger).
2. **Buffer backing memory is not guest-blob memory.** `PageBox` (16 KiB pages, PE allocator) and the readback `dst_ptr` must come from `WMTMemoryAlloc`/`WMTMemoryFree` (slot 153, L). No winemetal API change, but the PE allocator, free-after-release ordering and the `unix/shared` "PE pointer" contract change.
3. **`newLibraryWithSource` has no options** (7 compile sites; `preserveInvariance` and language/math mode matter). New function/slot or extended slot 144; wire change both sides. Also ASCII-only source.
4. **No texture/buffer/command-buffer property getters** (`textureType`, `sampleCount`, `usage`, `storageMode`, `label`, `device()`; ~35 sites). Prefer a Rust-side metadata table (no wire change); new QUERY slots otherwise.
5. **`supports32BitFloatFiltering`** (device.rs:225): one new QUERY slot, or derive.
6. **Capture**: `isCapturing`, `supportsDestination`, start result; host-path output.
7. **Descriptor labels** (pipeline, sampler, DSS) and `MTLFunction.name`: cosmetic; object labels are covered by slot 86.
8. **Queued creates hide nil**: `newDepthStencilState` (20), `newFunction` (26) are Q; mtld3d treats nil as failure.
9. Struct-default mismatches (not API gaps, must be filled): sampler (`max_anisotroy=1`, `normalized_coords=true`, `lod_max_clamp`), texture (`depth/array_length/sample_count/mip>=1`), pipeline (`rasterization_enabled=true`), stencil masks truncated to 8 bits.
10. ObjC assumptions: `Retained`/`ProtocolObject` typed objects, `borrow_retained` raw-pointer deref, `autoreleasepool`, `block2` (completion blocks, other agents' area). The `objc2-metal` types do not exist on Linux; the port needs a small handle-based facade in place of `ProtocolObject<dyn MTL...>` (descriptors become plain Rust structs filled into the `WMT*Info`).

#### Open questions
- How does the guest report a nil result of a sync create (`newTexture`, `newBuffer`, `newRenderPipelineState`) to a caller that branches on failure? Not checked in `marshal.c`/`calls.c`.
- Does a nil `newLibraryWithSource` options (slot 144) resolve to MSL 2.4 / Fast / non-invariant on the target macOS? If invariance can be expressed in the MSL source (position `[[invariant]]`), options might be avoidable; not verified.
- Should `mtld3d.so` call winemetal through its exported `__wine_unix_call_funcs` table from the unix side, or through the PE thunks? Either way each `unixcall_*` struct (winemetal_thunks.h) is needed on the Linux build; which is intended is open.
- `WMTMemoryAlloc` is only declared under `DXMT_GUEST_VM`: confirm mtld3d's PE/unix pair can reach it (PE thunk for slot 153 is local, `calls.c:394`), and who frees `PageBox` pages before Metal drops the buffer (existing mtld3d retention logic in `encoder.rs` handles the timing on macOS; the VM adds the region reuse rule).
- `MTLCreateSystemDefaultDevice` vs `WMTCopyAllDevices[0]` on a multi-GPU Mac host.
- Stencil: any D3D9 title relying on stencil masks above 0xFF? Depth32Float_Stencil8 has 8 stencil bits, so truncation looks safe.

#### mtld3d -> winemetal: command submission and encoding inventory

Scope: queues, command buffers, render/blit/compute encoding, fences/events, threads. Read-only research, worktree upstream-master.
Paths: mtld3d Unix crate = `build/wine-arm64-src/dxmt/mtld3d/unix/unix/src` (call it `U/`); winemetal = `build/wine-arm64-src/dxmt/src/winemetal` (`W/`, impl `W/unix/winemetal_unix.c`). All `U/` line numbers below are in `U/metal/command.rs` unless a file is named.

Findings that shape everything else:
- `encoder.rs` / `encoder/*` / `draw.rs` / `handlers.rs` / `encoder_service.rs` contain NO Metal encoder or command-buffer calls (only `didModifyRange` at encoder.rs:1656, and doc comments). The D3D9->Metal translation produces a flat `Command` array per `PassDescriptor` (CommandType enum, `unix/shared/src/commands.rs`), and ALL encoder calls are one replay loop: `encode_pass` (command.rs:2717-3510) plus `encode_leading_blits` (2276-2715). That loop is the porting surface and it is already shaped like a winemetal node list.
- Threads: API thread (PE) records; native "encoder" thread translates; native "submit" thread (per device) replays into Metal and commits (`submit_frame`, command.rs:518); native "presenter" thread (per device, `metal/presenter.rs`) acquires the drawable, encodes the present CB and commits. Metal calls for draws/blits happen on the submit thread only (or inline on the encoder thread for rare sync submits, mutually exclusive). Retirement waits (`wait_for_gpu_retire`, command.rs:249) run on the API/encoder thread. Source: docs/ARCHITECTURE.md "Threading model".
- Per frame (typical): 1 queue per device (device.rs:254, label "mtld3d"); 1 draw/frame CB (`mtld3d-frame-*`, command.rs:628); 0-1 upload CB (`mtld3d-upload-*`, 1117) holding the leading blit encoder plus the upload-prefix passes; 1 present CB (`mtld3d-present-*`, presenter.rs:994) with 1-3 fullscreen render passes; occasional snapshot CB (presenter.rs:749, one blit). Encoders: one render encoder per `PassDescriptor` (a pass per RT/depth switch or clear; count is game dependent, NOT measured here), plus a blit encoder per pass that has leading blits, plus the single frame-leading blit encoder. No compute encoder on the draw path (compute only in depth_transfer, rare). Measured encoder counts per frame: not found in docs; would need a PERF=1 run.
- Not used anywhere in mtld3d (so no work): fences (MTLFence), MTLEvent/MTLSharedEvent, encodeSignalEvent/encodeWaitForEvent, useResource/useHeap, argument buffers, indirect draws, instanced draws with baseInstance != 0, mesh/tile shaders, memory barriers, setViewports/setScissorRects (plural), setFrontFacingWinding, setDepthClipMode, fillBuffer, addScheduledHandler, enqueue, waitUntilScheduled, commandBuffer labels via anything but setLabel. Ordering between CBs is purely by commit order on the one in-order queue (upload CB committed before the draw CB, command.rs:~790-805).

#### Gaps ranked by size

1. Completion handlers (addCompletedHandler, 6 sites; 3 are load-bearing: frame, upload, present). LARGE, but contained: replace by a retirement thread per device that does `MTLCommandBuffer_waitUntilCompleted` + `MTLCommandBuffer_status` (+ `MTLCommandBuffer_property` for GPU time) on registered CBs in commit order and then runs the existing handler bodies. No winemetal change, no cmdlist.c change. The in-flight map (`PendingCmdBufs`) and `retire_finished` are already sequence-ordered and thread-agnostic. Cost: one blocking slot per CB (2-3 per frame) and wake latency; this feeds the frame-latency gate and PE recycle counters, so latency matters. The presented handler on drawables (command.rs:225, presenter `resolve_when_presented`) is the presentation agent's, same kind of gap.
2. Readback and upload memory model (blit_texture_to_buffer's `newBufferWithBytesNoCopy` over PE pointers; command.rs:3830). LARGE, but belongs to resources/platform agents; flagged because it sits inside a command-submission function. The blit commands themselves are covered.
3. #### Open questions

- Blocking slots: `waitUntilCompleted` (and `MTLSharedEvent_waitUntilSignaledValue`) can block for a whole frame. Does the VM's slot dispatcher run each call on its own host thread, or one serial thread? If serial, a retirement-wait slot would stall encodeCommands slots. (cmdlist.c/calls.c were not read for dispatch concurrency.)
- Native handler alternative: is a host->guest completion notification path (like `eac-vm/metal/wm/notify.h` used for shared-event listeners) acceptable instead of a guest-side wait thread? Cheaper per frame but a new slot plus a notify type.
- Command list size/payload limits: `MN_WM_MAX_NODES=65536` per call is stated; the data-length limit of one flattened list (`k->data_len`) and the per-call payload budget for SetBytes were not checked. Large passes may need chunking.
- Pass counts per frame in real games (encoders per frame) are not documented; measure with a PERF=1 run before deciding whether per-pass `renderCommandEncoder` + `encodeCommands` + `endEncoding` (3 slots/pass) is cheap enough or whether a combined "render pass + list" slot is worthwhile.
- Stencil reference: mtld3d passes `cmd.param_a` (u32) to `setStencilReferenceValue`; winemetal's `SetStencilRef` carries a u8. D3D9 stencil ref is a DWORD but values above 255 behave as masked by the stencil buffer anyway; confirm mtld3d masks upstream or mask at translation.
- `MTLCommandEncoder_setLabel` on a command buffer or queue: works via Obj-C selector but is outside its declared type; VM marshal checks handle kind only (`MN_HK_OBJC`). Verify before relying on it for CB labels.
- didModifyRange per call is a sync slot; on Apple Silicon it is a no-op for Shared storage. Decide with the resources agent whether the VM build skips it.
- Present-route command buffers (upscale/MetalFX `encodeSpatialScale`, HDR present, cursor overlay queues, gamma table `setFragmentBytes`) were only skimmed for queue/CB/encoder usage; their Metal-layer/drawable aspects are the presentation agent's.
- Not read in full: encoder.rs (10.5k lines) beyond grep (no Metal encoder calls found), encoder/ops.rs, encoder/compile.rs; `U/metal/upscale.rs` and `U/metal/macdrv/cursor_overlay.rs` bodies.

#### 4. Gaps ranked by size

1. **Presented-frame feedback** (large): `addPresentedHandler`/`presentedTime` is the signal that resolves the frame-latency pacing mark and detects "visible window shows nothing". No winemetal equivalent. Needs a new call (drawable presented -> `MTLSharedEvent` signal, or a pushed bit) plus a decision about what a forwarded round trip costs in the present loop (`presenter.rs:1060-1130`, `frame_signal.rs`).
2. **Command-buffer completion handlers and `block2`** (large; overlaps the encoding agent): the presenter, upscale eviction and diagnostics all use `addCompletedHandler` blocks. winemetal has events instead. Rewrite of present-buffer retirement (`presenter.rs:1021-1049`, `upscale.rs:440-470`).
3. **View lifecycle policy** (large, mostly deletion): parking/adoption/hosted views, `get_cocoa_window`, WineMetalLayer bypass, win32u client-surface presents, `client_view_watch`, WineWindow poking (`macdrv.rs:1309-2135`, `client_surface.rs`, `client_view_watch.rs`: ~2,000 lines). Must be either `cfg(macos)`-only (then "same source on macOS" is false for these) or reduced to `CreateMetalViewFromHWND`/`ReleaseMetalView`. This decides the macOS regression surface; needs the maintainer.
4. **Occlusion** (medium): no signal in winemetal. VM host window occlusion must reach the guest or the presenter pays the 1 s `nextDrawable` timeout per frame.
5. **Display and colour description** (medium): screen-native colourspace ("passthrough" default), ExtendedLinear DisplayP3 / BT.2020, `wantsEDR` independent of colourspace, per-layer display identity, panel `maximumFramesPerSecond` (needed for vsync throttle), `localizedName`. Partly covered by `getEDRValue`, `QueryDisplaySettingForLayer`, `GetDisplayDescription`; the rest needs new winemetal calls.
6. **Layer geometry read** (medium): `bounds`, to keep drawable == backing store. Plus `maximumDrawableCount`, background colour, gravity (small).
7. **crash.rs + shared/identity.rs + core/crash_report.rs Linux port** (medium): Mach VM calls, `__darwin_mcontext64`, Mach-O segment parser, `LC_UUID`. Mechanical but touches 1,436 + 1,137 (tests) lines.
8. **Metal HUD rows** (small-medium): State Reporter -> DeveloperHUDProperties labels, or drop.
9. **`MetalFX` `colorProcessingMode`** (small): add to `WMTFXSpatialScalerInfo`; required for the HDR upscale route.
10. **`newLibraryWithSource` options** (small): language version 2.4 and math mode for `present.msl`; or precompile.
11. **Build gating** (small): target-gated deps, `mod` cfgs, `.cargo/config.toml` Linux target, output name.
12. **Drops** (trivial, ~3,000 lines gone): cursor overlay, screen-parameter filter, NSProcessInfo activity, Main Thread Checker, `stack_page`, `translation`, `proc_pid_rusage`/`malloc_zone_statistics`.

#### 5. Open questions

1.
